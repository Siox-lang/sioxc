# E-P003: Incompatible types or shapes

A value does not fit the type required by a declaration, assignment, argument or return. Widths, declared array ranges and nominal types are part of that contract.

## Example

Compile this example with `sioxc --emit ir type_mismatch.siox`.

```siox
module type_mismatch;
fn value() -> integer {
    return 1.5;
}
```

## How to fix

Return an integer in this example, or change the declared result if a real is intended. For other mismatches, use a defined explicit conversion or construct the exact required shape; do not assume implicit resizing.

## Applied layouts

A scalar width must be at least one and fit the compiler's layout representation.
This also applies when a constant, function call or named template argument
determines a struct field, derived type or entity port width. Fix the arguments
at the primary span; a related label identifies the source layout. Inclusive
directional ranges may have negative labels: `-4..0` has five elements, not a
negative width. Unknown symbolic widths are not guessed to be invalid.

## Trait signatures

A trait implementation must honor the instantiated parameter and result types
declared by its trait. Aliases are transparent and `Self` names the implementing
type; assignment conversions do not silently adapt the method signature.
Keep the required signature and convert inside the body when appropriate, or
change the trait contract deliberately. The secondary label points to the trait
declaration that requires the type.

## Trait template arguments

Supply the number of arguments declared by the selected trait. Named arguments
must refer to its actual parameter names and cannot repeat a parameter. A type
parameter requires a type argument; a value parameter, such as `N: integer`,
requires a value. Forwarded generic parameters retain their declared kind, and
`Self` is a type. Fix the application first: invalid arguments prevent meaningful
comparison with the trait's method signatures. The related label identifies
the trait or template parameter declaration.

A value argument must also match its instantiated bound under ordinary
assignment-context rules. For `N: integer`, `1.5` is a real value; use
`integer(1.5)` if that conversion is intended. An integer literal can take a
real context. Aliases, contextual literals and source constant/function
contracts follow the same checks as ordinary arguments. Unknown generic or
opaque facts do not produce guessed errors; checking a type does not prove
that every value is compile-time evaluable.
